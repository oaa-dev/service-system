## Knowledge Context

### Relevant Learnings
- [Morph map solution](../knowledge/solutions/runtime-errors/enforce-morph-map-breaks-existing-polymorphic-models-chat-20260228.md): Polymorphic types use alias strings (`booking`, `reservation`, `service_order`, `inquiry`), not PHP class names — Flutter models must map these as string enums
- Auth module: Registration with `role=customer` → OTP verification → Bearer token. `onboarding` middleware passes through for customer role
- Re-registration guard: If unverified account exists, API resends OTP instead of creating duplicate — handle gracefully in registration screen
- Notification IDs are UUIDs (String in Dart, not int)
- Standard API response: `{success, message, data, meta: {pagination}}`

### Known Gotchas
- `z.coerce.number()` type mismatch from web frontend — not applicable to Flutter but shows validation edge cases exist
- OTP resend has 5-minute cooldown — show timer on OTP screen
- 401 response must clear auth state and redirect to login (replicate Axios interceptor behavior)

### Critical Patterns Applied
- Clean Architecture + BLoC (from brainstorm)
- API response wrapper with Either type for error handling
- Dio interceptor for auth token injection + 401 handling (mirrors web Axios client pattern)

## Overview

Set up the Flutter project skeleton at `mobile/` with Clean Architecture structure, core infrastructure (Dio API client, secure storage, theming, error handling), and the complete auth feature (login, register, OTP verification, profile fetch). This gives a solid foundation for all subsequent feature modules.

### Step 4: Implement core/error — Failure types + API response wrapper
- **Files:** `mobile/lib/core/error/failures.dart`, `mobile/lib/core/error/exceptions.dart`, `mobile/lib/core/network/api_response.dart`
- **Details:**
  - `Failure` sealed class: `ServerFailure(message, statusCode)`, `NetworkFailure(message)`, `AuthFailure(message)`, `ValidationFailure(message, errors: Map<String, List<String>>)`, `CacheFailure(message)`
  - `ServerException`, `AuthException`, `ValidationException` custom exception classes
  - `ApiResponse<T>` freezed model matching the backend shape:
    ```dart
    @freezed
    class ApiResponse<T> with _$ApiResponse<T> {
      const factory ApiResponse({
        required bool success,
        required String message,
        T? data,
        PaginationMeta? meta,
      }) = _ApiResponse;
    }

    @freezed
    class PaginationMeta with _$PaginationMeta {
      const factory PaginationMeta({
        required int total,
        required int perPage,
        required int currentPage,
        required int lastPage,
        int? from,
        int? to,
      }) = _PaginationMeta;
    }
    ```
  - **Knowledge note:** Backend always returns `{success, message, data, meta}`. Error responses add `errors` map for validation (422)

### Step 5: Implement core/network — Dio API client + auth interceptor
- **Files:** `mobile/lib/core/network/api_client.dart`, `mobile/lib/core/network/auth_interceptor.dart`, `mobile/lib/core/storage/secure_storage.dart`
- **Details:**
  - `SecureStorageService` — wraps `flutter_secure_storage` with `getToken()`, `saveToken()`, `deleteToken()`, `getUser()`, `saveUser()`, `deleteAll()`
  - `AuthInterceptor` extends `Interceptor`:
    - `onRequest`: reads token from SecureStorage, adds `Authorization: Bearer {token}` header + `Accept: application/json`
    - `onError`: if `response.statusCode == 401`, clears storage and navigates to login (via router ref or callback)
  - `ApiClient` class:
    - Wraps Dio instance with `BaseOptions(baseUrl: apiBaseUrl, connectTimeout: 30s, receiveTimeout: 30s)`
    - Adds `AuthInterceptor` + `LogInterceptor` (debug only)
    - Generic request methods: `get<T>()`, `post<T>()`, `put<T>()`, `patch<T>()`, `delete<T>()` that return `Either<Failure, ApiResponse<dynamic>>`
    - Catches `DioException` types and maps to `Failure` subclasses:
      - `DioExceptionType.connectionTimeout/receiveTimeout` → `NetworkFailure`
      - `statusCode 401` → `AuthFailure`
      - `statusCode 422` → `ValidationFailure` (parse `errors` map from response)
      - `statusCode 403` → `ServerFailure` with forbidden message
      - `statusCode 404` → `ServerFailure` with not found message
      - Other → `ServerFailure`
  - **Knowledge note:** Mirrors the Axios client behavior in `frontend/lib/axios.ts` — same 401 clear-and-redirect pattern

### Step 10: Implement auth feature — data layer
- **Files:** `mobile/lib/features/auth/data/`
- **Details:**
  - **Models (freezed):**
    - `UserModel` — `{id, name, first_name, last_name, email, email_verified_at, roles[], permissions[], merchant?, customer?}`
    - `AuthTokenModel` — `{token, token_type, requires_verification}`
    - `LoginRequest` — `{email, password}`
    - `RegisterRequest` — `{first_name, last_name, email, password, password_confirmation, role: 'customer'}`
    - `VerifyOtpRequest` — `{otp: String(6)}`
    - `VerificationStatusModel` — `{is_verified, can_resend, locked_until, expires_at}`
  - **Data source (remote):**
    - `AuthRemoteDataSource` — calls ApiClient for:
      - `POST /auth/login` → `AuthTokenModel`
      - `POST /auth/register` → `AuthTokenModel`
      - `POST /auth/verify-otp` → `{message}`
      - `POST /auth/resend-otp` → `{message}`
      - `GET /auth/verification-status` → `VerificationStatusModel`
      - `GET /auth/me` → `UserModel`
      - `POST /auth/logout` → `{message}`
  - **Data source (local):**
    - `AuthLocalDataSource` — wraps SecureStorageService for token + cached user
  - **Repository implementation:**
    - `AuthRepositoryImpl` — combines remote + local, returns `Either<Failure, T>`
    - On login/register success: saves token to secure storage
    - On logout: clears all secure storage
  - **Knowledge note:** Registration with `role=customer` auto-creates a Customer record on the backend. Re-registration of unverified email silently resends OTP — detect via `requires_verification: true` and navigate to OTP screen

### Step 11: Implement auth feature — domain layer
- **Files:** `mobile/lib/features/auth/domain/`
- **Details:**
  - **Entities:**
    - `User` — domain entity (can be same as UserModel for now, or a simplified version)
  - **Repository interface:**
    - `AuthRepository` — abstract class defining all auth operations returning `Either<Failure, T>`
  - **Use cases** (one class per use case, each has a `call()` method):
    - `LoginUseCase(AuthRepository)` → `Either<Failure, User>`
    - `RegisterUseCase(AuthRepository)` → `Either<Failure, bool>` (true if requires verification)
    - `VerifyOtpUseCase(AuthRepository)` → `Either<Failure, void>`
    - `ResendOtpUseCase(AuthRepository)` → `Either<Failure, void>`
    - `GetVerificationStatusUseCase(AuthRepository)` → `Either<Failure, VerificationStatus>`
    - `GetCurrentUserUseCase(AuthRepository)` → `Either<Failure, User>`
    - `LogoutUseCase(AuthRepository)` → `Either<Failure, void>`
    - `CheckAuthStatusUseCase(AuthRepository)` → `Either<Failure, bool>` (has valid token?)

### Step 12: Implement auth feature — presentation layer (BLoC)
- **Files:** `mobile/lib/features/auth/presentation/bloc/`
- **Details:**
  - **AuthBloc** — manages overall auth state:
    - Events: `AuthCheckRequested`, `AuthLoginRequested(email, password)`, `AuthRegisterRequested(...)`, `AuthLogoutRequested`
    - States: `AuthInitial`, `AuthLoading`, `AuthAuthenticated(user)`, `AuthUnauthenticated`, `AuthError(message)`, `AuthNeedsVerification`
    - On `AuthCheckRequested`: check secure storage for token → if found, fetch `/auth/me` → `AuthAuthenticated` or `AuthUnauthenticated`
    - On login success: if `requires_verification` → emit `AuthNeedsVerification`, else fetch user → `AuthAuthenticated`
    - On register success: always emit `AuthNeedsVerification` (customer registration requires OTP)
    - On logout: clear storage, emit `AuthUnauthenticated`
  - **OtpBloc** — manages OTP verification flow:
    - Events: `OtpSubmitted(code)`, `OtpResendRequested`, `OtpStatusChecked`
    - States: `OtpInitial`, `OtpLoading`, `OtpSuccess`, `OtpError(message)`, `OtpResent`, `OtpCooldown(seconds)`
    - Cooldown timer: 5-minute resend cooldown from backend — show countdown
    - **Knowledge note:** Backend returns `locked_until` timestamp — calculate remaining seconds from that

## Risks and Mitigations

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Flutter SDK version mismatch on dev machines | Medium | Pin Flutter version in `pubspec.yaml` + document in README |
| Reverb WebSocket auth in Flutter (later phase) | Medium | Deferred to messaging phase; this phase is HTTP-only |
| `freezed` code generation issues | Low | Pin `build_runner` + `freezed` versions; add generated files to `.gitignore` or commit them |
| Secure storage not available on web/desktop | Low | This is a mobile-only app; web customer portal already exists |
| API base URL config across environments | Low | Use `--dart-define=API_URL=...` or `.env` file with `flutter_dotenv` |
